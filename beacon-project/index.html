Beacon 계획서

1. 프로젝트 개요

여러 대의 서버·컨테이너에서 개별적으로 운영 중인 모니터링/알림 도구의 상태 정보를 하나의 대시보드로 통합하여 보여주고, 이상 상황 발생 시 Discord·이메일로 실시간 알림을 전송하는 웹 기반 관제 시스템을 기획·구현한다.

개인이 자체 서버를 운영하면서, 그리고 팀 단위로 여러 서비스를 나눠 운영하면서 실제로 겪은 "서비스별로 상태 확인 창을 여러 개 띄워놓고 봐야 하는" 불편함에서 출발한 프로젝트로, 가상의 문제가 아니라 팀 내에서 어차피 필요로 하던 도구를 구체화했다는 점에서 실용성이 명확하다.

2. 배경 및 필요성

  • 자체 인프라나 팀 프로젝트 서버를 운영하다 보면 목적별로 서로 다른 도구를 함께 쓰게 되는 경우가 많고, 팀원마다 담당하는 서비스가 다르면 이 문제는 더 커진다.
  • 각 도구는 자체 웹 UI와 알림 채널을 따로 가지고 있어, 전체 인프라 상태를 한눈에 파악하기 어렵고 알림도 여러 곳에서 따로 온다.
  • 기존 통합 솔루션(Grafana 등)은 기능이 방대한 만큼 설정이 무겁고, 개인/소규모 팀 환경에는 과한 경우가 많다.
  • 또한 대부분의 통합 도구는 사전에 정의된 몇 개 서비스만 지원하기 때문에, 팀에서 자체적으로 만든 서비스나 스펙이 다른 외부 서비스는 붙이기 어렵다.
  • → "가볍게, 우리가 쓰는 도구들만 골라서, 새로운 서비스도 쉽게 붙여가며 통합" 하는 확장 가능한 경량 대시보드를 직접 만들어보는 것이 프로젝트의 핵심 동기.

3. 프로젝트 목표

  1. 서로 다른 소스(모니터링 툴 API, 자체 상태 확인 엔드포인트, 외부 서비스의 웹훅)의 상태 데이터를 하나의 백엔드로 수집·정규화한다.
  2. 수집된 상태를 실시간(WebSocket)으로 대시보드에 반영한다.
  3. 임계치·장애 조건을 설정하면 Discord Webhook / 이메일로 알림을 보낸다.
  4. 정해진 몇 개 서비스만이 아니라, 설정만으로 새로운 서비스를 추가 연동할 수 있는 확장 구조를 갖춘다.
  5. 개인·팀 서버 환경에서 실제로 사용 가능한 수준의 완성도를 목표로 한다.

4. 주요 기능 명세

4.1 MVP (필수 기능)

  • 모니터링 대상 서비스 등록/삭제 (이름, 엔드포인트, 체크 주기)
  • 주기적 헬스체크(HTTP ping / TCP 포트 체크) 및 상태 저장
  • 웹훅 수신 엔드포인트: 외부 서비스가 보내는 JSON을 받아 저장 (자주 쓰이는 1~2개 포맷 기준 매핑)
  • 실시간 대시보드 (전체 서비스 상태 카드 뷰, 정상/경고/장애 색상 구분)
  • 서비스별 상세 페이지 (최근 상태 이력, 응답시간 그래프)
  • 장애 발생 시 Discord Webhook 알림

4.2 웹훅 수신 구조 (핵심 차별점)

기존에 등록된 서비스를 주기적으로 "찾아가서 확인(polling)"하는 방식만으로는, 서비스가 먼저 상태를 "알려주는(push)" 구조를 지원하지 못한다는 한계가 있다. 이를 보완하기 위해 다양한 서비스가 서로 다른 형태의 JSON Body로 보내는 웹훅을 공통 포맷으로 받아들이는 구조를 둔다.

  • 엔드포인트: POST /webhook/{service-slug} — 서비스별로 고유 URL 발급
  • 서비스 등록 시 관리자가 필드 매핑 규칙을 지정 (예: 상태 값은 status, 메시지는 message, 심각도는 level 필드에서 추출)
  • 매핑 규칙에 따라 원본 JSON을 내부 공통 이벤트 포맷(serviceId, status, message, severity, timestamp)으로 변환 후 저장
  • 아직 매핑 규칙이 없는 새 서비스는 원본 JSON을 그대로 저장해두고, 이후 매핑 규칙만 추가하면 코드 수정 없이 연동 가능
  • 이 구조 덕분에 "미리 정해진 몇 개 서비스만 지원"하는 기존 통합 도구와 달리, 설정만으로 새로운 외부 서비스를 계속 붙여나갈 수 있다 → 프로젝트의 "확장성" 주장의 실질적 근거

4.3 확장 기능 (시간 여유 시)

  • 필드 매핑 규칙을 코드 수정 없이 웹 UI에서 직접 설정 (JSON 경로 지정 방식)
  • 이메일 알림 (SMTP)
  • 알림 규칙 커스터마이징 (연속 실패 N회 이상일 때만 알림 등, 노이즈 억제)
  • 다운타임 통계 (일간/주간 가동률 %)
  • 사용자 인증 (로그인 후 본인 대시보드만 조회)

7. 화면 설계 (개요)

  1. 메인 대시보드: 등록된 서비스 카드 목록, 상태별 색상(정상/경고/장애), 마지막 체크 시각
  2. 서비스 상세 페이지: 응답시간 추이 그래프, 최근 장애 이력, 체크 주기 설정
  3. 서비스 등록/연동 페이지: 헬스체크 방식 또는 웹훅 방식 선택, 웹훅 선택 시 필드 매핑 규칙 입력
  4. 알림 설정 페이지: 알림 채널 등록(Discord Webhook URL), 알림 조건 설정
  5. (확장) 통계 페이지: 서비스별 가동률, 기간별 장애 횟수

9. 기대 효과 및 차별점

  • 무겁고 범용적인 Grafana류 솔루션 대신, 팀·개인 규모에 맞는 경량 통합 관제 도구를 직접 설계·구현해봄으로써 시스템 설계 역량을 증명할 수 있다.
  • 사전에 정의된 몇 개 서비스만 지원하는 기존 통합 도구와 달리, 웹훅 기반의 범용 수신 구조를 갖춰 코드 수정 없이 설정만으로 새로운 서비스를 계속 연동할 수 있다 — 이것이 "통합"을 넘어 "확장 가능한 통합"이라는 프로젝트의 핵심 주장.
  • 실제 운영 중인 인프라나 팀 프로젝트 서버에 바로 적용 가능한 결과물이라, "만들고 끝"이 아니라 지속적으로 쓸 수 있는 프로젝트.
  • 비동기 스케줄링, 웹훅 처리, 실시간 통신, 알림 연동 등 백엔드 개발의 핵심 요소를 종합적으로 다룸.

10. 리스크 및 대응 방안

리스크대응 방안
일정 내 확장 기능까지 구현 어려움MVP 우선 개발, 확장 기능은 우선순위 낮춰 시간 남을 때 진행
서비스마다 제각각인 JSON 구조 대응 복잡도우선 자주 쓰이는 1~2개 포맷 위주로 매핑 지원, 완전 범용 매핑 UI는 확장 단계로 분리
WebSocket 실시간 처리 복잡도초기엔 polling 방식으로 먼저 구현 후 WebSocket으로 교체하는 단계적 접근

이 초안을 바탕으로 발표용 슬라이드나 기능별 상세 설계(ERD, API 명세, 웹훅 매핑 규칙 스키마 등)도 이어서 작성 가능합니다.
