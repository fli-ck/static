# 01. 개요

> 최초 작성: 2026-09-23

## 1. 한 줄 정의

**Beacon은 여러 인프라 도구의 상태를 한곳으로 모으고, 자연어로 조회·조작할 수 있게 하는 팀용 에이전틱 대시보드다.**

## 2. 왜 필요한가

팀 인프라는 이미 여러 도구가 나눠서 지키고 있다. Uptime Kuma는 가동 여부, Sentry는 에러, Beszel은 리소스, 외부 클라우드는 자체 상태 페이지와 웹훅. 각 도구는 자기 화면과 자기 알림을 갖고 있어서, 전체 상태를 보려면 창을 여러 개 띄워야 하고 알림도 여러 곳에서 따로 온다.

통합 솔루션(Grafana 등)은 이 문제를 풀지만 두 가지 비용이 있다. 설정이 무겁고, 미리 만들어둔 화면에 없는 질문을 하려면 쿼리 언어를 배워야 한다.

Beacon은 두 번째 비용을 자연어로 바꾼다. **화면을 늘리는 대신 에이전트가 쓸 도구를 늘린다.**

## 3. Beacon이 하는 것 · 하지 않는 것

| 한다 | 하지 않는다 |
| --- | --- |
| 원천 시스템의 상태를 **읽어서** 모은다 | 직접 헬스체크하지 않는다 (D1) |
| 외부 웹훅을 받아 저장한다 | 모니터를 등록·관리하지 않는다 (D12) |
| 자연어 조회에 답한다 | LLM에게 실행 권한을 주지 않는다 |
| 점검을 생성한다 (kuma-bridge 경유, 사람 승인 후) | Kuma에 직접 쓰지 않는다 (D10) |
| 역할별로 권한을 나눈다 | 비밀번호를 쓰지 않는다 (D26) |

## 4. 사용 예시

```
"지금 문제 있는 서비스 있어?"
"오늘 점검 일정 있어?"
"내일 새벽 3시부터 2시간 forgejo 점검 잡아줘"
"최근 웹훅 중에 ap-northeast 리전 incident만 요약해줘"
"지난주에 가장 오래 죽어 있던 서비스는?"
```

앞의 넷은 읽기, 세 번째만 쓰기다. 쓰기는 확인 카드를 거쳐 사람이 승인해야 실행된다.

## 5. 구성 요소

| 구성 요소 | 위치 | 역할 |
| --- | --- | --- |
| Beacon | `beacon.prdis.me` | 대시보드, 에이전트, 인증, 어댑터, 웹훅 수신 |
| kuma-bridge | `kuma-bridge.thrush-ide.ts.net` | Kuma Socket.IO API를 REST로 감싼 서버. 별도 저장소 |
| maintenance 봇 | 기존 | Discord 기반 점검 관리. kuma-bridge의 또 다른 소비자 |
| Uptime Kuma | 기존 | 모니터와 점검 일정의 원천 |
| tsidp | 테일넷 | 신원의 원천 |

세부 구조는 `02-architecture.md`.

## 6. 성공 기준

**과제로서**

- 최종 발표에서 아래 데모가 끊김 없이 동작한다
  1. 테일넷에서 tsidp로 로그인, 외부 도메인에서 패스키로 로그인
  2. 대시보드에 Kuma 모니터 상태가 실시간 반영
  3. 자연어로 상태 조회, 웹훅 이벤트 요약
  4. 자연어로 점검 생성 → 확인 카드 → 승인 → Kuma에 실제 생성
  5. Viewer 계정으로는 같은 지시에 쓰기 도구가 보이지 않음
  6. 감사 로그에서 방금 한 일이 전부 추적됨

**실사용 도구로서**

- 팀원이 Kuma 화면 대신 Beacon을 먼저 연다
- maintenance 봇과 Beacon이 같은 점검을 두 번 만들지 않는다

## 7. 발표 포인트

| 질문 | 답 |
| --- | --- |
| 그냥 Grafana 쓰면 되지 않나? | Grafana는 쿼리 언어를 배우게 한다. Beacon은 자연어로 같은 일을 한다 |
| 직접 만든 게 뭔가? | 어댑터 구조, 에이전트 절충 구조, 패스키 인증, kuma-bridge |
| 에이전트가 마음대로 하지 않나? | LLM은 함수일 뿐. 도구 목록은 역할로 걸러지고, 쓰기는 상태 기계와 사람 승인을 거친다 |
| 왜 비밀번호가 없나? | 신원은 tsidp가, 외부 접속은 패스키가 맡는다 |
